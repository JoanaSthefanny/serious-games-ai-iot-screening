# Serious Games AI-IoT Screening

Semi-automated screening pipeline for systematic mapping studies involving **serious games**, **artificial intelligence (AI)**, **Internet of Things (IoT)** technologies, and **health applications**.

This repository provides an organized and updated implementation of the research software developed to support title, abstract, and keyword screening.

The pipeline combines:

- database-specific metadata import;
- metadata standardization;
- DOI recovery;
- keyword consolidation;
- internal and cross-database duplicate detection;
- persistent master-record identifiers;
- Springer metadata enrichment;
- LLM-assisted evidence classification;
- deterministic screening rules;
- conservative safety-rescue mechanisms;
- checkpoint-based execution;
- human-review routing.

The system was designed to prioritize screening sensitivity and reduce the risk of automatically excluding potentially relevant studies.

---

## Research Context

The original systematic mapping study investigates studies that simultaneously involve:

1. Serious games or equivalent game-based interventions;
2. Health-related applications;
3. Artificial intelligence;
4. Internet of Things technologies or functionally IoT-compatible architectures.

The automated stage assists screening by classifying available evidence and applying transparent deterministic rules.

Final eligibility decisions remain under human supervision.

## Using the Pipeline for Other Reviews

The metadata-processing architecture can serve as a starting point for other systematic reviews or systematic mapping studies.

Relatively reusable components include:

- bibliographic metadata import;
- metadata standardization;
- DOI recovery;
- keyword consolidation;
- duplicate detection;
- master-dataset management;
- checkpoint-based execution;
- API-error handling;
- Excel output generation.

The screening classifier is **topic-specific**.

Researchers adapting it should revise:

- the screening prompt;
- structured classification fields;
- domain-specific lexical signals;
- deterministic decision rules;
- safety-rescue rules;
- output fields and summaries;
- prompt and classifier versions;
- calibration material.

## Screening Architecture

The workflow consists of:

1. Search the bibliographic databases;
2. Export and place metadata in the corresponding local directory;
3. Import and standardize bibliographic records;
4. Recover DOIs and consolidate keywords;
5. Deduplicate records within each database;
6. Update the master dataset and resolve cross-database duplicates;
7. Enrich Springer metadata when required;
8. Obtain structured evidence classifications from Gemini;
9. Apply deterministic rules, including safety rescues;
10. Route records to human review.

Gemini does not directly determine final study eligibility.

Its role is to assign structured evidence labels and supporting justifications. Python determines the automated screening outcome.

---

## Screening Outcomes

### `RETAIN`

The metadata supports all four core eligibility dimensions, with no unresolved gamification-only or secondary/incomplete label.

The study should proceed to subsequent assessment.

`RETAIN` does not represent definitive full-text inclusion.

### `UNCERTAIN`

The evidence requires human review because of unresolved labels, contradictory game/gamification labels, a safety rescue, or a missing abstract.

An uncertain label does not override an earlier exclusion rule.

### `EXCLUDE`

An exclusion rule applies, including a negative core criterion that is not covered by a safety rescue.

The detailed rule precedence is documented in [docs/decision_rules.md](docs/decision_rules.md).

Technical failures are handled separately from these eligibility outcomes.

---

## Conservative Screening Strategy

The screening guidance follows this principle:

> Automatic exclusion should be supported by evidence of absence; incomplete descriptions should be assessed conservatively.

AI methods, connected architectures, or game components may only be fully described in the article's full text.

Nevertheless, the deterministic layer excludes a record with a negative core criterion unless a documented rescue applies, even when another label is uncertain.

Safety rescues preserve selected cases for review. They do not relax the final eligibility criteria.

## Screening Prompt

The current operational Portuguese prompt is:

```text
prompts/screening_prompt_v1_9_pt.txt
```

Earlier prompt files, when retained, represent previous versions rather than the active configuration.

An English translation is documentation material unless the classifier is explicitly configured to load it.

Prompt loading is controlled by these components in `src/screening/classifier.py`:

```text
PROMPT_FILE
PROMPT_VERSION
DEFAULT_PROMPT
load_screening_prompt()
```

The loader uses the external prompt when it exists and contains text. Otherwise, it uses the embedded fallback.

Keep the external prompt and embedded fallback consistent when modifying the configuration.

## Metadata Standardization

Database exports are converted into a common bibliographic representation.

Core fields include:

```text
master_id
source_id
database
title
authors
year
publication
document_type
doi
abstract
keywords
url
metadata_status
metadata_source
```

Volume metadata is preserved when available to help distinguish records with similar titles.

Title and abstract content are carried into the standardized records. Normalized representations are used internally for operations such as duplicate detection.

See [docs/data_format.md](docs/data_format.md) for the detailed schema.

### DOI Recovery

When a dedicated DOI field is empty, the importer searches applicable metadata fields for DOI-compatible strings.

For example:

```text
https://doi.org/10.1007/s11036-025-02473-6
```

is normalized to:

```text
10.1007/s11036-025-02473-6
```

### Keyword Consolidation

Applicable keyword fields are combined rather than selecting only one source.

Examples include:

- Scopus author and index keywords;
- PubMed other terms and MeSH headings;
- Compendex author, controlled, and uncontrolled terms.

For Compendex BibTeX exports, index terms may also be recovered from `key` and `note`.

## Importing Records

Before importing:

1. Perform the database search;
2. Export the metadata;
3. Place the exports in `data/raw/<database>/`.

Select **Import records [1]** and choose the database.

Standardized outputs are written under `data/processed/`, including:

```text
ieee_records.xlsx
pubmed_records.xlsx
acm_records.xlsx
scopus_records.xlsx
compendex_records.xlsx
springer_records.xlsx
```

An import that produces no records does not overwrite the previous processed output.

Internal deduplication preserves the table schema and recovers missing bibliographic fields from duplicates when available.

Compendex BibTeX entries rejected only because of repeated copyright fields can be recovered. Other rejected BibTeX blocks stop that import rather than silently producing a partial result.

## Master Dataset and Duplicate Detection

The master dataset is stored at:

```text
data/processed/master_records.xlsx
```

Unique records receive persistent identifiers:

```text
MASTER-0001
MASTER-0002
MASTER-0003
```

Existing identifiers are preserved when new records are added.

Matching prioritizes normalized DOI, followed by normalized title where the match is suitable.

Volume conflicts and ambiguous title matches are considered to avoid merging distinct proceedings records.

Duplicate reports support auditing of the consolidation process.

## Springer Metadata Enrichment

Springer exports may lack abstracts.

The enrichment component queries the Springer Nature Meta API using available identifiers and metadata.

Configure `SPRINGER_API_KEY` and select **Enrich Springer metadata [3]**.

The process:

- preserves existing abstracts;
- attempts retrieval when needed;
- saves progress;
- records unsuccessful retrieval attempts.

Records whose abstracts cannot be retrieved remain available for human assessment.

A retrieval failure does not establish ineligibility.

## Semi-Automated Screening

Select **Run semi-automated screening [4]**.

The screening menu supports an individual database or all configured databases.

Each database produces a separate screening workbook.

Gemini evaluates:

1. Serious game;
2. Gamification only;
3. Health;
4. Artificial intelligence;
5. Internet of Things;
6. Secondary or incomplete publication type.

The response contains structured labels and supporting evidence.

The deterministic layer then assigns the screening outcome.

Health applications include physical activity when the study connects the solution to a health purpose, such as prevention, rehabilitation, sedentary behavior reduction, or functional capacity.

Generic activity or sports performance alone does not automatically establish a health application.

## Deterministic Decision Rules

The current decision order is:

1. Contradictory serious-game and gamification-only labels;
2. Secondary or incomplete study;
3. Gamification only;
4. Safety rescues;
5. Negative core criteria;
6. Uncertain labels;
7. Retention.

When `serious_game = YES` and `gamification_only = YES`, the result is `UNCERTAIN` with an empty rescue code.

This contradiction is checked before study type.

A negative core criterion causes exclusion unless a rescue applies. An uncertain label does not override that exclusion.

See [docs/decision_rules.md](docs/decision_rules.md) for complete definitions.

---

## Safety-Rescue Mechanisms

The current classifier implements four rescues, evaluated in this order:

| Code | Required conditions |
|---|---|
| `RESGATE_IOT_3_DE_4` | Serious game, health, and AI are `YES`; IoT is `NO`; an acquisition or monitoring signal is present. |
| `RESGATE_MULTIMODAL` | Health and AI are `YES`; serious game or IoT is `NO`; both interaction and acquisition signals are present. |
| `RESGATE_AAL_ESTIMULACAO` | Serious game is `NO`; health is `YES`; AI is `YES` or `UNCERTAIN`; IoT is `EXPLICIT_IOT` or `FUNCTIONALLY_COMPATIBLE`; stimulation and assistive-platform signals are present. |
| `RESGATE_AAL_METADADOS_INCOMPLETOS` | Secondary/incomplete and gamification-only labels are `NO`; serious game and AI are `NO`; health is `YES`; the AI justification matches supported omission cues without a blocking cue; IoT is `EXPLICIT_IOT`, `FUNCTIONALLY_COMPATIBLE`, or `UNCERTAIN`; acquisition, assistive-platform, and stimulation-review signals are present. |

Signals are checked against calibrated terminology and helper functions in `src/screening/classifier.py`.

The AAL metadata-omission rescue also checks predefined phrases in the AI justification and notes. These checks can miss paraphrases and are not a general semantic detector.

There is no generic three-of-four rescue or independent game, health, or AI terminology rescue.

All four rescues return:

```text
UNCERTAIN
```

They do not confirm eligibility or automatically include a study.

The AAL metadata-omission rescue preserves the original criterion labels and routes the record to full-text review.

Safety rules are topic-specific and must be reassessed when adapting the pipeline.

---

## Records Without Abstracts

A missing abstract is not interpreted as evidence of absence.

Records without abstracts receive:

```text
decision = UNCERTAIN
api_status = NO_ABSTRACT
```

They remain available for human assessment.

This handling is separate from the four safety-rescue rules.

## Checkpoints and Technical Failures

The screening process saves results incrementally.

When resuming, saved results are reused only when their recorded metadata and configuration satisfy the checkpoint compatibility checks.

Changes to metadata, prompt content, model, or version identifiers can invalidate previously saved results.

API errors remain technical outcomes rather than eligibility exclusions. Failed analyses can be retried.

Checkpoint write failures stop execution without converting a successful classification into `API_ERROR`.

The previous checkpoint is replaced only after the new workbook has been fully written.

Preserve historical workbooks and use separate output paths when comparing configurations.

## Reproducibility Notes

The pipeline records:

```text
model
prompt_version
classifier_version
```

alongside screening results. Checkpoints also use metadata and prompt fingerprints when available.

The deterministic classifier, prompt, and public software release have separate version identifiers.

Historical results retain the identifiers recorded by their original execution. The current prompt and classifier versions must not be assigned retrospectively to those results.

LLM outputs may vary because of model behavior, provider updates, API changes, and service conditions. A new execution is not guaranteed to reproduce every historical classification.

For research reporting, preserve:

- the code revision used;
- the prompt content and version;
- the classifier version;
- model and execution settings;
- input metadata;
- generated outputs;
- human assessment records.

When citing this repository, identify the release or commit corresponding to the implementation being discussed.
